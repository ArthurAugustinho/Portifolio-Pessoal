## The problem

Clinics and doctors’ offices that schedule appointments by phone, paper or
spreadsheet live with a predictable set of failures: overlapping time slots,
cancellations nobody records, a patient showing up on a day the doctor does not
see patients. Each of these errors turns into rework for the secretary and
waiting for the patient.

The aggravating factor is that the four people involved — patient, doctor,
secretary and administrator — work with different information that is out of
sync between them. The schedule the doctor sees is not the same one the
secretary consults.

Before writing code, I conducted the project’s field research: conversations
with clinics to understand how scheduling happened in practice and where it
broke down. That stage defined the scope — the problem was not a lack of
systems, it was the lack of a system where the four profiles saw the same data.

## What I built

I was responsible for the application’s **backend**, in Java 17 with Spring
Boot 3.

The API exposes the operations of the four profiles, each with distinct
permissions over the same data:

**Patient** searches for doctors by specialty, checks availability, books and
cancels appointments.

**Doctor** manages their own schedule, edits their professional profile and
moves appointments between the pending, confirmed and cancelled states.

**Secretary** registers patients, reschedules and cancels appointments, manages
schedules.

**Administrator** manages users, approves or rejects doctor registrations and
accesses statistics.

Authentication with JWT and BCrypt passwords, input validation with Bean
Validation, versioned migrations with Flyway, DTO mapping with MapStruct and API
documentation in Swagger. Unit tests with JUnit 5 and Mockito.

## Decisions

**Clean Architecture on the backend.** The code is split into four layers:
`domain` with pure entities and rules, `application` with use cases,
`infrastructure` with JPA repositories and configuration, and `interfaces` with
controllers and DTOs. It costs more files than Spring’s standard package
structure, but it keeps the business rules independent of the framework and the
database — swapping Hibernate for something else would not touch the domain.

**PostgreSQL with versioned migrations.** Scheduling is a domain of rigid
relationships: a time slot belongs to one doctor, an appointment occupies
exactly one slot, two patients do not occupy the same one. That is a key and
transaction constraint, not a flexible document. Flyway ensured the schema
evolved identically on every machine of the team and in production.

**Cutting hospital criticality detection.** The original scope included a
severity triage module, for use in a hospital setting. After assessing the
complexity — risk classification has clinical implications, it is not just
business logic — we decided to remove it and deliver clinic and doctor’s-office
management well. It was the kind of feature that would have consumed the entire
deadline and been left half-finished.

**Containers on ECS Fargate.** Backend and frontend in Docker containers, images
in ECR, database on RDS. For a team of four with nobody dedicated to
infrastructure, managing EC2 instances would have consumed time that went into
the application instead.

## Architecture

The application is in two parts, in separate repositories: a Next.js frontend
and a Spring Boot backend, talking over a REST API. The backend is a modular
monolith — one application, one database — organised in the four layers of Clean
Architecture.

RDS and a load balancer in front. Deployment is automated with GitHub Actions.


## Outcome

The system was delivered with the complete flow working: registration, doctor
search by specialty, booking, confirmation and cancellation, with the four
profiles operating on the same data. The backend accumulated 256 commits over the
course of development.

As a capstone project, it was developed throughout the degree in Software
Engineering, between 2022 and 2025.

Pass+ never had real clients and is no longer hosted — validation was done in a
test environment, not in clinic operation.

## What was left out

- Detection of hospital criticality, cut as a scope decision
- Medical history linked to an electronic health record
- Integration with public health systems such as e-SUS
- SMS notifications — only email was implemented
- Load testing in real production
